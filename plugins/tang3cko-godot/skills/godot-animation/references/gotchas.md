# Animation Gotchas (Distinct From Retarget Math)

These bugs survive a correct two-sided retarget — they come from scene authoring and gameplay wiring around the animation, not from the retarget pipeline itself. All fail **silently** (no error, no warning), which is why they belong in a checklist rather than relying on noticing them.

## Hand-authored MeshInstance3D missing its `skeleton` NodePath

When a character scene is generated by the engine's own FBX import, the `MeshInstance3D`'s `skeleton` property is wired automatically. When a `.tscn` is instead hand-authored — placing a `MeshInstance3D` as a child of a `Skeleton3D` by hand — that implicit wiring does **not** happen.

Symptom: the `Skeleton3D` itself is working correctly (querying its bone poses at any point in time returns the right values), but the mesh renders frozen in its bind/rest pose regardless — the GPU skin never re-deforms. No error, no warning; only a rendered frame reveals it (numeric checks on the skeleton pass cleanly).

Fix: every `MeshInstance3D` under a `Skeleton3D` in a hand-authored scene needs its `skeleton` NodePath explicitly set (typically `NodePath("..")` pointing at the parent).

## Skin bind pose not recomputed after a rest change

When a character scene is regenerated on a normalized skeleton (after retarget rest_fixer changes the rest pose), the skin's bind pose must be recomputed from the **new** rest, or the mesh renders visibly warped even though the skeleton's bone data is correct. Recompute bind poses as part of any workflow step that changes rest pose.

## Mesh forward axis mismatch

Don't assume a character mesh's un-rotated forward direction — confirm it by rendering the character from a fixed camera angle with no rotation applied, rather than trusting the engine's general forward-axis convention. A mesh whose authored forward axis doesn't match the convention your movement/orientation code assumes (e.g. a `LookAt`-based facing system) will walk backward, and this error compounds: any other transform tuned assuming the "normal" forward convention (a seat marker's rotation, a spawn orientation) will be tuned against an already-wrong assumption, appearing as two seemingly unrelated bugs with one root cause. Fix at the mesh-instance transform level (a single corrective rotation applied once, e.g. in the code that assigns the mesh to a character), not by special-casing every downstream consumer.

## Clip length vs. actual hold/stay duration

A transition pattern driven by an animation-finished signal only fires if the clip is allowed to play to completion. If the gameplay state holding that animation ends (state timer, despawn, etc.) before the clip's full length, the transition **never fires** — not intermittently, reliably never, for every instance where the state duration is shorter than the clip. This is easy to miss because the clip looks correct in isolated preview (where nothing cuts it short).

Check the actual numeric relationship (clip length vs. state hold duration) whenever wiring a finished-signal-driven transition off a clip that wasn't specifically authored to fit the hold window. If the full clip doesn't fit, either trim what portion of the clip actually needs to play and drive the transition off a timer scaled to playback speed, or shorten/lengthen the hold state to fit the full clip — don't leave the transition wired to a signal that structurally cannot fire.

## Checklist

- [ ] Every `MeshInstance3D` under a `Skeleton3D` in a hand-authored `.tscn` has its `skeleton` NodePath explicitly set — verified in the scene file, not assumed from the importer's behavior
- [ ] Any workflow step that changed a skeleton's rest pose also recomputed the skin's bind pose from the new rest
- [ ] The mesh's un-rotated forward axis was confirmed by rendering, and any needed correction is a single rotation at the mesh-instance level — no downstream consumer special-cases it
- [ ] For every finished-signal-driven transition: clip length vs. state hold duration compared numerically, and the transition restructured (timer or hold-window change) if the full clip cannot play out
